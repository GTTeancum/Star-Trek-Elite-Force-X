## Findings, ordered by impact

### 1. The surviving lighting policy has no measured FPS benefit

Current `code/renderer/tr_init.cpp:164` enables the policy automatically for direct-map co-op when `r_efCoopPerformance` is zero, explicitly enables it for positive values, and permits a negative benchmark control. `code/renderer/tr_bsp_xbox.cpp:493` skips optimized world lightmaps. `code/renderer/retail_xbox/tr_scene_retail.cpp:1257` suppresses dynamic lights during actual cooperative split mode. Frontend new-game/load and console launch paths set the policy.

This is real work removal and a visible lighting tradeoff, not proof of higher FPS. Lightmaps can share a draw through multitexture (`tr_shader.cpp`, `CollapseMultitexture`), so “removes lightmap passes” must not be translated into a guaranteed reduction of draw calls. Host emulation bottlenecks can dominate the saved work.

The three `ps2coop_vertexlight_off_normal_20260917[a-c].summary.json` files have zero accepted gameplay samples. The first two end live but fail mode verification. The last lacks final state and its report records process exit at 129.3 seconds, return code 3489660927, after native capture failed to find the module base. This does not establish whether the exit was a game failure, host failure, or external termination. All three transaction manifests say restored. There is no completed lighting-on/off pair to calculate a ratio from.

Disposition: **implemented, limited quality evidence, performance unproven; not a qualified stable release improvement.** Do not invent an FPS percentage or resume repeated trials by default. Preserve the authorized change for an explicit keep/disable decision; a rollback of unrelated VV/memory work would not answer this question.

### 2. The 0.918× claim is arithmetically correct but overstates comparison precision

`ps2coop_quality_normal_20260917b` versus `ps2coop_full_ratio_normal_20260917a` share XBE `64b2c8b5...`, 230-second requested duration, map and replay. Both summaries report two players, liveness and empty errors. Their accepted results are 9.0365027149 versus 8.2944940359 **guest elapsed FPS**, five windows each. The quotient is 0.9178876, approximately -8.21%.

However, the actual accepted windows differ. Control samples 20–24 end at server times 89478–98589 ms; candidate samples 19–23 end at 86485–95227 ms. A shared input replay and duration do not establish identical scene/combat workloads. These numbers are not native XEMU frames per host second, and the five windows do not establish repeatability. They cannot be sold as an exact visible-FPS regression on this PC, much less on Xbox hardware.

Both runs have lighting enabled: the control's missing positive cvar did not disable the automatic co-op lighting policy. The comparison concerned the now-removed model-array path, not lighting.

Disposition: **reject the unproven array candidate under the user's clear-win rule; retain the numbers as limited negative evidence, not a calibrated regression percentage.** Current `win_qgl_dx8.cpp` no longer contains the `r_efCoopModelArrays` path. The primary push buffer is back to 1024 KiB in `win_main_console.cpp:1531`.

### 3. PS2 observations were promoted into Xbox recommendations too quickly

Sol first described PS2 `r_subdivisions=10` as producing fewer polygons, then checked the actual Xbox code and correctly reversed that conclusion. The Xbox baseline is forced to 64; lowering the tolerance creates more subdivisions. Keeping 64 was the correct decision.

Likewise, on-disk indexed geometry in a PS2 loader does not establish GPU submission cost, model-path behavior, or a missing optimization in the Xbox renderer. The normal Xbox path already submits indexed geometry; the older expanded-array/hybrid experiments are separate paths. The prior recommendation blurred these distinctions. The existence of PS2 visibility cvars also does not prove the exact Xbox model-PVS algorithm is used on PS2.

The preserved R5900 exports are useful evidence, with explicit provisional-decompilation limitations. The earlier generic MIPS output and failed compressed-layout interpretation of CD.PMP are superseded. Keep the archive/hash/geometry work; do not call every subsequent Xbox idea a technique demonstrated by PS2.

Disposition: **no additional clear, qualified co-op FPS winner established by this audit.** An empty candidate list is acceptable.

### 4. The test workflow repeatedly failed its own entry conditions

Seven of the nine September 17 `ps2coop*.summary.json` files have zero accepted gameplay samples. Repeated `wait; exitview` attempts depended on rendered-frame progress on a slow host and repeatedly failed to establish two-player gameplay in time. Those are invalid performance runs, not evidence for or against an optimization.

The new slice-warp run is also a synthetic fixture, not natural campaign progression. Transaction metadata says `diagnostic_only=false` despite `borg1_slice_warp_requested=true`; the latter and `visual_only=true` must be retained when interpreting it. Do not treat that label as campaign qualification.

Recent runs use mutable `build/release` symbols rather than the complete immutable bundles required by the project. This does not prove a mismatch happened, but weakens provenance and makes subsequent reuse unsafe after a build. Existing source-string assertions in `verify_coop_ps2_renderer.py` pass, but establish wiring only, not correct shading, mode transitions, or FPS.

Disposition: **stop fixed-duration retry loops and stop using build success or tool exit code zero as runtime success.** Any future explicitly authorized comparison must first establish runtime two-player gameplay and actual workload; compare native frame-counter deltas over equivalent gameplay intervals on this same machine at Normal priority. Never invert MSPF. Do not require this weaker PC to match the original PC's absolute FPS.

## Memory work: supported but narrower than full stability

The preserved same-binary Deck09 index-stream comparison demonstrates 548,864 extra physical bytes free during three loading phases, at a cost of 73,952 extra zone bytes used. It is a transient loading improvement; it did not demonstrate a global minimum or steady-state RAM saving. The PS2 loader itself allocates whole temporary lumps, so per-surface streaming is an independently justified Xbox improvement, not a direct copy of PS2 streaming behavior.

The matched MDR frame-codec bridge runs use XBE `dbfe2e2853...` and both end live/error-clear. Previously recorded fresh physical minima are 221,184 control versus 634,880 candidate; final free physical bytes are 1,433,600 versus 1,855,488. This is useful memory evidence, not an FPS result or a full save/travel qualification.

This audit completed the pending independent offline validation against the preserved candidate 64 MiB guest snapshot. All animation bytes in the four resident hazardfemale/crewthin lower/upper models match their source assets: **6,619,208 bytes across 12,218 frames**. Result: `notes/evidence/audit_20260917/resident_mdr_validation.json`. This checks resident encoded content using an independent decoder, not every live frame-cache access, animation pose or transition. The JSON's saved-byte figures compare resident representation against source files; they are not the incremental benefit over the previous codec.

Disposition: **preserve these memory changes and evidence; no detected byte corruption in that snapshot.** Repeated transitions, saves, all affected content and low-memory margins remain unqualified. Do not conflate this memory result with the PS2 co-op FPS hunt.
